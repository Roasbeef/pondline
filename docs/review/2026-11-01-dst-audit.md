# DST audit, 2026-11-01

The audit phase of the deterministic simulation test for the real shell
(two daemons and a mailbox), taken at `3f57317`. It is the evidence the
plan in `docs/dst/plan.md` rests on. Numbers were measured with the
commands named; anything not measured is marked.

Everything was measured in a scratch worktree at `3f57317`. The coverage
driver is `scripts/dst/cov.erl` (usage below).

---

### 1. Scope and premise

**Subsystem.** Two client daemons (`daemon/node` `rest_for_one` trees) and one mailbox (`mailbox/node`), running the real shell. Several stateful processes in one VM, with I/O at every edge, so a DST is the right tool. `node_test` already runs two daemons and a mailbox in one VM; `process.new_name` makes the names unique.

**Processes and what each owns**

| Process | Owns |
|---|---|
| daemon `engine` | The one SQLite connection; serializes every job. |
| `store` | Not a process; the engine's connection. |
| `scheduler` | `in_flight` map and the `batches` list of open weft runs. |
| `fetcher` (one per queue) | State `Acking`/`Polling`/`BackingOff`; `failures` count. |
| `fetch_manager` | `running` map from queue to fetcher pid. |
| `provisioner` | `failures` count and the named `scan` timeout. |
| `carrier` | Tor handle and bootstrap run state. |
| `status` | The Tor and mailbox status cell. |
| `events` | The subscriber list. |
| `lock` | The `lock.db` transaction. |
| `local_api` hub | The single runtime subscription and its waiters. |
| mailbox `coordinator` | The only connection; every request runs as one transaction. |
| `notifier` | Map from queue to waiting subjects. |
| `sweeper` | A periodic tick. |
| node long poll | Runs in the caller's process: a wait on the notifier. |
| `http` (mist) | One process per connection. |

**Boundaries where the outside world enters**

- **Network.** `transport.Dialer` (`policy` plus an injected `dial_onion` that returns a `Connection` of three closures) is reached through `mailbox_client.call`. HTTP framing is `core/http1`. The deadline comes from `daemon/internal/ffi_clock` (monotonic).
- **Daemon store.** `store.commit`/`transaction` (`BEGIN IMMEDIATE … COMMIT`) and about 20 reads, all asked through `engine.run`, which is `mail.ask` with a 30 s `process.receive` timeout.
- **Mailbox.** `service.handle`, reached as `node.handle` → `coordinator.handle`, whose `ask` also uses `process.receive`.
- **SQLite** through sqlight/esqlite. Every esqlite NIF is `ERL_NIF_DIRTY_JOB_IO_BOUND`.
- **Weft timers:**
  - `actor.periodic`: `scheduler.tick_ms`, `fetch_manager.tick_ms`, `sweeper`.
  - State timeouts: `fetcher` backoff (`with_state_timeout`).
  - Named timeouts: `provisioner` `scan`.
  - Run deadlines: `scheduler.send_batch`, `fetcher.start_run`, carrier bootstrap.
  - `poll.until`: `api.await_file`, `node.wait_for_lock`.
  - Raw `process.receive` timeouts: `mail.ask`, `coordinator.ask`, `notifier.forget`, `node.wait_for_append` (the long poll), `local_api_backend`.
- **Clocks.** Wall clock via `config.clock` (daemon) and `node.Config.clock` (mailbox). Monotonic via `ffi_clock`, `ffi_local_system` and `mailbox_ffi`.
- **Randomness.** `Suite.random` (ids, inboxes, capabilities, `agent_id`). Also the keypair and encapsulate functions, which in the real suite draw from OTP's own RNG (`crypto:generate_key`, `encapsulate_key`). The mailbox has no randomness except `create_grant(random)`.
- **Tor sidecar** through `carrier`.
- **Lifecycle.** Supervisor restarts, `node.stop`/`start`.

**Existing tests that call themselves a simulation.** Only `core/test/core/simulation_test.gleam` with `world.gleam`. It is a pure model of three parties with its own modelled shell, mailbox and scheduler. Besides it: `pairing_test`, `hardening_test`, a little qcheck in `mailbox/service_test`, and no property tests in `daemon`.

**CI.** None exists. There is no `.github`, `.circleci`, `.gitlab-ci.yml` or `.buildkite`; `docs/next.md` item 3 still lists CI as to-do.

### 2. Audit

#### Coverage (Erlang `cover`)

This works and is exact. A driver module `cov.erl`:

1. cover-compiles each production module from its package's `build/dev/erlang/<pkg>/ebin/<mod>.beam`, finding modules from `src/**/*.{gleam,erl}` with `/` mapped to `@`;
2. runs every module under `test/` through `eunit:test(Mods, [{scale_timeouts,10}])`, which is what gleeunit does without its `halt`;
3. writes `cover:analyse(M, coverage, line)` and the zero-call functions from `cover:analyse(M, calls, function)`.

Invocation, from the package directory after `gleam test` has built it, with `dangerouslyDisableSandbox`:

```
REEDWIRE_TOR_BIN=… erl -noshell -pa build/dev/erlang/*/ebin -pa <dstcov> \
  -eval 'cov:run(["<out>", "daemon", "mailbox", "core"])'
```

`cov:only([Out, TestMod | Pkgs])` restricts the run to one test module. Line numbers map to `.gleam` source lines. The `@external` wrapper modules (`ffi_local_socket` and similar) show 0% as an artifact.

| Scenario | Rate |

**Where the core simulation spends its time.** Under `eprof` of one chaotic test, 73.5% goes to `core@crypto@fake_suite:lane/3` (46.5M calls). That is the fake SHA-256, which consumes one byte per call into a 64-bit multiply, and it runs over every padded envelope. TLV decoding is the remainder. `eprof` inflates call-heavy functions, so the true share is likely lower.

**Where a shell DST would spend its time.** A daemon-store commit to a file costs 4,886 µs per write, because of `fullfsync`. With `:memory:` it costs 10.4 µs; reads cost 17.9 µs and 12.6 µs. That is about 470× (`bench.erl`). `file:<name>?mode=memory&cache=shared` works through `store.open` unchanged: a second connection sees the data and a write costs 8.0 µs (`mem.erl`). The mailbox store takes the path as given. So stores need no fault-free seam beyond a path override in the daemon. I did not profile `node_test`; that fsync dominates its 0.42 s is an estimate (tens of commits × about 5 ms).

#### Input space and corpus

- Each case is approval (0–1) × budget (0–4) × 160 picks of (0–100000, 0–100000). It cannot be enumerated.
- Every run uses fixed qcheck seeds, about 227 schedules: 3 × 25 chaotic, 4 × 8 benign, and a 40-case sample. Every run explores the same schedules.
- There is no swarm: rare steps are switched per step by `choice mod k`, never per seed, so every seed has every fault class on.
- `fake_suite.random` draws from `erlang:unique_integer`, so ids depend on test order. The world does not branch on id bytes as far as I read, but the generator is not seeded.

#### The four false-pass shapes in the core simulation

**1. Properties never checked**
- Liveness in any run with the clock, `Close`, `Decline` or `Expire`: the delivery audit is benign-only.
- That held messages are released after `Raise`: the settle only approves.
- That receipts name only messages that were actually sent.
- Closed-stays-closed: phase monotonicity.
- Bounded outbox and processed growth (spec §13.1, bounded work).

**2. Fault classes never generated**
- Mailbox refusals: Quota, BadDeadline, Conflict, Unauthorized, Unavailable.
- Mailbox loss after a receipt (retention sweep).
- Clock skew between parties and the mailbox: the world has one `now`.
- An authenticated byzantine peer: a repeated message id, wrong-phase control messages.
- An operator-visible ambiguous outcome: a commit or ask that applied, then a retry.
- `HeldFull`: 160 steps can never fill 256 held messages.

**3. A heal step that hides a bug**
`settle`/`pump` retransmits every outbox row every round. The world mailbox has no tombstones and `wire_send` re-appends after an ack. Production does neither: the scheduler stops at `Stored`, and the mailbox answers a retransmit from its tombstone. So when a mailbox corrupts a stored envelope, the daemon drops and acks it, and the message is lost in production. The benign audit passes because the heal re-delivers it. In production this needs a corrupting mailbox, so it is a policy gap (see policy question 5).

**4. A test that asserts the bug**
None found. I checked `check_delivery_allowed` (the ADR-004 exemption is intended), the `HeldFull` drop-and-ack (documented intended in `plan.gleam`), and `audit_delivery`'s `row.1 != plan.Expired` filter (dead since 42d4f6f, harmless).

#### What the pure model cannot see

- Weft timers and run deadlines (`Abandoned`/`NeverStarted`).
- The engine's version-checked commit and `fault()` mapping.
- The scheduler's concurrent batches, the per-row `in_flight` bookkeeping, and immediate re-dispatch.
- Fetcher ack→poll rounds, `try_each` head-of-line behaviour, and liveness retirement.
- The provisioner and fetch manager.
- Supervisor restart recovery.
- SQLite constraints (UNIQUE on deliveries) and ambiguous commits.
- An ask that applies and then errors (engine `run` → `Unavailable`).
- The mailbox's long poll, notifier, tombstones, deadline validation and sweeper.
- HTTP framing.
- The carrier and the sidecar.

#### Likely live bugs (hypotheses, unverified)

- **H1. Clock skew makes sends fail permanently.** The default lifetime equals `limits.message_retention_seconds` (604,800; `relationship.gleam:964–966`). The mailbox accepts only `deadline <= now + retention` with no slack (`service.insert_new`). `BadDeadline` is classified as permanent `Refused` (`scheduler.classify_refusal`), which leads to `store.Rejected`. A sender whose clock leads the mailbox by more than the dispatch delay plus latency therefore fails application messages, and also receipts and control messages such as Accept, which use the same retention. **Probe:** daemon clock = mailbox clock + 5 s; send; expect `failed`.
- **H2. An authenticated peer can poison a queue with a repeated message id.** Core does not deduplicate message ids (`admit` only counts).
  - At 3f57317, `INSERT OR IGNORE INTO deliveries` hides the duplicate while `budget.used` counts it twice.
  - With the other agent's uncommitted change to a plain `INSERT`, the commit fails, `engine.process` returns `Unavailable`, the round fails and the envelope is never acked. `process_batch` uses `try_each`, so every later envelope on that queue stalls forever.
  - **Probe:** a byzantine-peer op that seals two Applications with the same id.
- **H3. Scheduler send storm after a failed `record_send`** (being fixed now). Covered under recall below.
- **H4. API outcome unknown.** `send`/`invite`/`accept` return `Unavailable` after a commit lands (store ack lost, or the ask timed out after the job ran). An operator retry duplicates the message, the offer (consuming mailbox queue allowance), or the relationship (a second joiner relationship stuck in `AwaitingAccept`).

### 3. The virtual-time bubble on BEAM

#### Timers: what weft gives today (0.4.6)

| Primitive | Injected source? | Call sites needing a seam |
|---|---|---|
| `weft/actor` `periodic` and `idle_timeout` | Yes: `actor.with_timer_source(timer.Injected(after:))` | `scheduler.builder` (223), `fetch_manager.builder` (109), `sweeper.builder` (54) |
| `weft/state_machine` state, named, event and periodic timeouts | Yes: `sm.with_timer_source` | `fetcher.start` (296), `provisioner.builder` (182), and the `tor` machine if it is put in the bubble |
| `weft` run `deadline` / `cancel_grace` | **No.** `process.send_after` on the wall clock (`weft.gleam:2020`, `2983`) | `scheduler.send_batch` (416), `fetcher.start_run` (309), `carrier` bootstrap (218). Needs a weft extension such as `weft.with_timer_source(run, source)`. |
| `poll.until` | `poll.until_on(clock:)` exists | `api.await_file` (291) and `node.wait_for_lock` (404) call `until`; both need a clock from config |
| Raw `process.receive` timeouts | n/a | `mail.ask` (74) and `coordinator.ask` (197) never fire in a sim of responsive processes, so they need no seam unless ask timeouts are a fault. `node.wait_for_append` (227) **is** a must: the real 25 s long-poll wait would stall each round in real time. `notifier.forget` (121) and `local_api_backend` (279) can stay. |

#### Clock
- `daemon/config.clock` and the mailbox `node.Config.clock` exist.
- `mailbox_client`'s monotonic deadline (`ffi_clock`) can stay, because the simulated `Connection.receive(max, timeout)` honours the timeout argument in virtual milliseconds. Optional seam: a clock in `Dialer`.

#### Randomness
- `config.suite` is injectable, but the real suite's `x25519_keypair`, `ed25519_keypair`, `kem_keypair` and `kem_encapsulate` use OTP's internal RNG.
- I found no seeded ML-KEM in OTP: `crypto:generate_key(mlkem1024, [], <<0:512>>)` raises `Can't EVP_PKEY_new_raw_private_key`.
- So the bubble needs a deterministic suite: the core fake suite with a seeded counter instead of `unique_integer`, made fast by hashing 8 bytes per step. It must be shared with the daemon tests, because test modules of a dependency are not compiled into dependents. Real X25519 and Ed25519 from seeded secrets is possible, but the KEM still has to be fake.

#### Message ordering: the options weighed

- **(a) `+S 1` alone.** Not deterministic. esqlite runs on dirty IO schedulers, there are wall-clock timers, and reduction-based preemption interleaves concurrent chains. Cheap (`ERL_FLAGS="+S 1"`); useful only as a complement.
- **(b) Runner plays the event loop.** Expose each actor's handler and step it from the runner. On weft this means re-implementing `sm.Next` and `actor.Next` interpretation (transitions, timeouts, selectors) in the harness, which mocks weft. Not recommended.
- **(c) Quiescence-stepped bubble with real processes (recommended first).**
  - Every external event parks at a boundary the runner owns: simulated network requests and responses, virtual timer armings, operator ops.
  - The runner releases one event, then waits until the VM is quiescent: `erlang:statistics(total_active_tasks_all)` equal to 1, stable across a yield, through a test FFI.
  - The runner then sorts the ready set by a stable key and shuffles it with the seed.
  - Residual nondeterminism comes only from fan-out inside one causal chain. Chiefly, `engine.commit_change` → `notify` tells the scheduler, provisioner, fetch manager and events at once, and they race to the engine's mailbox. Several fetchers also race to the engine.
  - Those engine jobs are reads, or commits to disjoint relationships, so the divergence should be rare. The double-run snapshot must measure it.
- **(d) Add a mail and ask interception seam** so cross-actor asks and tells park with the runner too. This gives exact replay. It costs a handle type change in every worker `Config` (`Name(engine.Message)` becomes a handle carrying a mailer), about 25 call sites. That is the same churn the daemon `CLAUDE.md` already declines for `weft/registry`. Do it only if (c)'s double-run shows divergence.

#### Stores
- Shared-cache in-memory SQLite (`file:dNN?mode=memory&cache=shared`, with a keeper connection held by the harness so restarts keep data). It keeps full SQL strictness (UNIQUE, foreign keys, transactions) at about 8 µs per write.
- Caveat: journal mode becomes `memory`, and a second writer gets `LOCKED` rather than `BUSY`, which only matters for outside-lock tests.
- `lock.db` stays a real file.

#### Network
- Plug a simulated `Dialer` into the daemon: `dial_onion` returns a `Connection` whose `send` captures the HTTP request (a split on `\r\n\r\n`, then `codec.decode_request`) and parks it.
- The runner later calls the real `mailbox/node.handle` in a per-request process, so a long poll blocks only that process. It encodes the response with `codec.encode_response` and HTTP framing, and `receive` returns it.
- Client-side framing (`mailbox_client`, `http1`) is kept; mist and `mailbox/http` are skipped.
- Faults then need no production change:
  - drop the request;
  - apply, then lose the response (the ambiguous Append);
  - delay or reorder;
  - mailbox down;
  - byzantine responses (corrupt, truncated, wrong receipt, every Refusal kind);
  - kill the coordinator.

#### Seams to add (nil or `WallClock` by default)

- **`daemon/config.Config`:**
  - `timer: timer.Source` (default `WallClock`);
  - `dialer: Option(Dialer)` (default `None`, which keeps `carrier.dialer`);
  - `database: Option(String)` (path override);
  - `store_faults: Option(store.Faults)`;
  - `engine_faults: Option(fn(JobKind) -> JobFate)`;
  - `poll_clock: poll.Clock`.
  
  `node.launch` threads these into the child configs.
- **`daemon/store`:** `open_with(path, suite, faults)`; `transaction` consults the hook before `BEGIN` (Down: nothing written, error) and after `COMMIT` (AckLost: written, error). SQLite transactions are atomic, so there is no torn mode.
- **`daemon/engine`:**
  - `Run(job, kind)` gains a `JobKind` label;
  - `handle` consults `engine_faults`: `FailBeforeApply` replies `Error(Unavailable)`; `ApplyThenFail` runs the job and replies `Error(Unavailable)`.
  
  One site covers all about 25 engine calls, and no mail seam is needed for ask faults.
- **Workers:**
  - `scheduler.builder`, `fetch_manager.builder`: `actor.with_timer_source(config.timer)`;
  - `fetcher.start`, `provisioner.builder`: `sm.with_timer_source`;
  - run deadlines in `scheduler.send_batch`, `fetcher.start_run` and `carrier`: the weft extension;
  - `fetch_manager` passes `timer` into `fetcher.Config`.
- **`daemon/api.await_file` and `node.wait_for_lock`:** `poll.until_on(clock: …)`.
- **`mailbox/node.Config`:**
  - `timer: timer.Source`, kept in `Node`;
  - `wait_for_append` selects on `wake` or an injected timeout subject instead of `process.receive(wake, ms)`;
  - `sweeper` gets `actor.with_timer_source`.
- **weft:** `weft.with_timer_source(run, Source)`, used by `deadline` and `cancel_grace`. It is a sibling repo; per `docs/weft.md`, extend it rather than forcing a fit.
- **Optional, for carrier recall:** a sidecar interface seam in `carrier` (bootstrap, dial, subscribe to restarts), so a fake sidecar can crash and restart.

#### Guards
- Each seam has a test that starts a node with defaults.
- A lint rule: no `src` module constructs `timer.Injected` or a fault hook.
- The deterministic suite lives under `test/` only (spec §13.3).

### 4. Depth answers

- **Raw material.** The real `daemon/node` trees, meaning engine, store, scheduler, fetchers, fetch manager, provisioner, events, status and lock, plus the real mailbox coordinator, notifier, sweeper, `service.handle` and long poll, driven through `daemon/api`. Replace only the dialer (simulated network into `mailbox/node.handle`), the timer source, the clocks, the suite's entropy and the SQLite file location.
- **Instruments.**
  - Weft `Injected` timer sources plus a virtual timer wheel.
  - Quiescence stepping via `erlang:statistics(total_active_tasks_all)`.
  - Seeded swarm seeds with a mode byte, a fault mask and ops.
  - Double-run snapshot of both stores and the network trace.
  - Erlang `cover` via `cov.erl`.
  - qcheck for the pure layer.
  - Recall through `recall.sh` with hand patches.
  - A Gleam mutation script in the shape of the repo's "mutation-test the timeout" practice. gremlins is Go-only.
- **Target with a guard.** Targets, all estimates: shell DST at 100 seeds/s or more per VM for two daemons plus a mailbox with about 64 ops, against today's 2.4 end-to-end scenarios/s; core sim at 60 cases/s or more, from 17.4; DST-only coverage of the daemon and mailbox runtime at 90% or more, from 80.4% under all existing tests; blind recall of 4 of the 6 applicable known fixes. Guard: production behaviour unchanged except confirmed fixes; every seam defaults to `WallClock`/`None` and is tested unset.
- **Judge.** Blind recall (table below) with runs-to-find; the double-run divergence rate; `cover` numbers per module; the mutation score on scheduler, fetcher, engine and service; and `/advisor-review` of the harness. Not my opinion of it.

### 5. Plan

#### Ranked proposals (yield per effort; effort is an estimate)

1. **Store and engine fault seams** (`store.transaction` Down/AckLost; engine `FailBeforeApply`/`ApplyThenFail`). *Small.*
   - Closes: the ambiguous-commit and ask-after-apply classes; the missed lines at scheduler 579 and store 1174.
   - Should find: H3 (scheduler storm), H4 (API outcome unknown).
   - Highest yield in the neutrino case.
2. **Shell DST skeleton.** Shared-memory stores, a simulated network through a dialer override, a deterministic suite, virtual timers via weft `Injected` plus the long-poll seam, quiescence stepping, operator ops, and an oracle at quiescence (below). *Medium to large: the weft run-deadline extension plus about 6 builder seams.* This is the bulk of the bug yield.
   Oracle at quiescence:
   - no Append whose bytes are not in a committed outbox;
   - no Ack of an id without a committed `Processed` row;
   - no message delivered twice;
   - budget books match deliveries;
   - every committed row decodes;
   - at most one in-flight Append per envelope;
   - after the heal phase: every committed message delivered once and receipted once, and every invite exportable.
3. **Network faults** at the simulated dialer: drop, apply-then-lose, mailbox down/up, reorder, byzantine responses, clock skew per node. *Small once item 2 exists.*
   - Closes: the 0% mailbox paths (`replay`, `same_queue_or_conflict`, sweep) and the scheduler/fetcher outcome arms.
   - Should find H1.
4. **Byzantine authenticated-peer ops** (repeated message id, wrong-phase controls) and operator inputs at and past the limits (description length around 256 bytes, budgets). *Small.* Should find H2 and the description-bound class.
5. **Speed and campaigns for the core sim.** A word-at-a-time fake hash (73.5% of time) for about 3–4× (estimate), a seeded counter for `random`, a seed or swarm entry point, a per-seed fault mask. *Small.*
6. **Fix the core sim's heal phase.** Outbox status, stop resending at `Stored`, mailbox tombstones, liveness for close and clock runs, a `HeldFull` reach. *Medium.* Mostly surfaces policy gaps.
7. **Restart and churn ops.** Kill engine, scheduler, fetcher or coordinator at quiescence; full `node.stop`/`start` over the same stores. *Small.* Medium yield; `recovery_test` covers the basics.
8. **Exact determinism via mail interception.** *Medium, with API churn.* Only if item 2's double-run diverges.
9. **Sidecar seam plus sidecar-churn fault.** *Medium.* Only for the carrier class.
10. **CI for `make check`**, then a nightly swarm. *Small.*

**Full plan:** items 1–10.

**Cheaper plan:** items 1, 2 without exact determinism, 3, 4 and 5. It drops:
- the mail seam, so replay is best-effort with a measured divergence rate;
- the core-sim heal rework;
- the sidecar seam, so no carrier recall;
- restart churn beyond whole-daemon restart;
- the nightly job.

#### Policy questions

1. How much scheduler nondeterminism to accept: measured divergence with excuses, versus exact replay through the mail seam?
2. Should an envelope that fails `engine.process` N times be quarantined (dropped and acked), or keep blocking its queue (H2)?
3. Should a duplicate message id from an authenticated peer be deduplicated in core, or treated as state divergence and fail? This bears on the in-flight `INSERT OR IGNORE` → `INSERT` change.
4. Should `send`/`invite`/`accept` take an idempotency key, so a retry after `Unavailable` cannot duplicate (H4)?
5. Is end-to-end retransmit on a missing receipt in scope? Today a mailbox that loses or corrupts a stored envelope loses the message.
6. Should the mailbox clamp or allow slack on the deadline, or should the sender shorten the default lifetime below retention (H1)? And should `BadDeadline` stay permanent?
7. Should the fixed run deadlines (fetcher poll 120 s, scheduler 130 s, ask 30 s) become progress-based?
8. Is a byzantine mailbox in scope (ignores tombstones, serves corrupt bytes)? This decides whether the id-and-digest rule is DST-reachable.
9. May the heal phase restart the carrier or sidecar? (Recommend no.)
