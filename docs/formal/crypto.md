# Verifying CryptoProfileV1: a symbolic proof and standard vectors

Pondline's cryptography is checked at two layers here. The pairing
handshake, as `core/crypto/pqxdh` runs it, is modelled in ProVerif and its
security properties are proved under four adversary scenarios, with a
leaked invitation, and against a set of deliberately broken variants that
each have to produce an attack. Underneath, every primitive the profile
uses is run against the published Wycheproof and NIST ACVP vectors through
the `primitives` API the protocol actually calls. The sealed invitation of
ADR-009 has a model of its own, built the same way.

The verdict: `check.sh` exits 0, with all 30 rows matching.

Every property the profile claims for the handshake holds in every scenario
where it should, and fails where it should not (a leaked invitation lets its
holder redeem it, and prekey secrets that are not retired forfeit forward
secrecy). Every broken variant produces its attack in the scenario the table
names. The bindings answer
every vector the way the protocol needs, including the implicit-rejection
secrets of ML-KEM and the key checks FIPS 203 asks for. The findings below
are about what the profile relies on that it does not say, and about one
place where the hybrid construction is weaker than its rationale: none is
a vulnerability in the implemented protocol.

The models live in `formal/crypto/`, the vectors and their tests under
`packages/primitives/test/`.

## Running it

`check.sh` needs `proverif` and `cpp` on `PATH`; nothing else finds the
prover. The opam package `proverif` depends on lablgtk for the interactive
simulator, so build ProVerif 2.05 from the source tarball instead:

- Download `https://bblanche.gitlabpages.inria.fr/proverif/proverif2.05.tar.gz`
  (SHA-256 `4871f53c32ab4a04669a060c4886ba5d9080496963fb980a9a62d2c429ceabc4`).
- Under an OCaml opam switch (`brew install opam`, `opam init --bare`,
  `opam switch create default 5.2.1`), run `./build` in the unpacked
  directory.
- Keep the directory anywhere and put it on `PATH` for the command, for
  example `/Users/roasbeef/tools/proverif-2.05`.

Tamarin was considered and not used: the queries are trace properties
(secrecy, injective agreement, equalities between event arguments) over a
two-message protocol, which ProVerif handles directly; it is the tool the
prior PQXDH analysis used, so the model can be read against that work; and
its attack traces come out of the same run as the proofs, which is what
the broken variants need.

```sh
PATH=/Users/roasbeef/tools/proverif-2.05:$PATH formal/crypto/check.sh   # about 23 min at -j 2
formal/crypto/check.sh -j 4 -k        # four provers, keep logs in formal/crypto/out
formal/crypto/check.sh base leak      # named rows only
cd packages/primitives && gleam test  # the vectors, with the rest of the suite
```

`check.sh` preprocesses `pairing.pv.in` and `ticket.pv.in` with `cpp` once
per row of its table, runs ProVerif on each, and compares the `RESULT`
lines with the row's expectation, one letter per query: `T` must be
proved, `F` must be refuted with a trace. An inconclusive query ("cannot
be proved") never matches. The exit status is zero only when every row,
including every row that expects an attack, matches. Each output line
ends with the row's wall time in seconds.

`formal/crypto/out/` is generated by `check.sh -k`, which deletes and
rewrites it, and is ignored by git. Nothing in this document depends on a
committed log; the raw lines below come from rerunning the script.

## Threat model

The attacker is the network and the mailbox: it reads, drops, reorders and
forges every message on the public channel, and it can register any
number of identities and prekeys of its own. The invitation file is an
out-of-band channel (a table in the model) that the attacker does not read
unless a scenario says so. Honest inviters and joiners run unboundedly
many sessions, each with a fresh pairwise identity, which is what the
profile prescribes (`identity.gleam`: "the keys are generated fresh per
relationship").

The hybrid construction is tested by giving the attacker one half of each
pair at a time. Each capability is a destructor the attacker can apply,
not a reveal of honest secrets, so nothing else about the parties
changes:

| Macro | The attacker can |
| --- | --- |
| `BREAK_DH` | compute the X25519 agreement of any two public keys |
| `BREAK_ED` | forge an Ed25519 signature under any public key |
| `BREAK_ML` | forge an ML-DSA-65 signature under any public key |
| `BREAK_KEM` | decapsulate any ML-KEM-1024 ciphertext |
| `WEAK_KEM` | re-encapsulate: turn a ciphertext into a different one with the same shared secret under the same key (the KEM is not ciphertext-binding) |
| `LEAK_INVITATION` | read the invitation file (the bundle) |
| `REVEAL_LT` | learn both parties' identity secrets after every session has ended (ProVerif phase 1) |
| `REVEAL_PREKEYS` | as `REVEAL_LT`, plus the inviter's signed prekey and ML-KEM prekey secrets |
| `REVEAL_LT_BEFORE` | learn both parties' identity secrets before the session |

The four hybrid scenarios are `base` (nothing broken), `quantum`
(`BREAK_DH BREAK_ED`: a quantum adversary breaks both Curve25519
schemes), `pq_broken` (`BREAK_KEM BREAK_ML`: both lattice schemes fail)
and `break_dh` alone. The first three also run with the leaked invitation;
`break_dh` has no leaked row of its own, and `no_sig_leak_dh` is the row that
combines the two.

## What is modelled

`formal/crypto/pairing.pv.in` follows the code, not the profile document,
where the two could differ (they do not; see the differences section).
The inviter process is `pqxdh.generate_prekeys` and `pqxdh.respond`
(`respond`, `pqxdh.gleam:499`), followed by the `Accept` the inviter encrypts from
the state `respond` returns (`relationship.gleam`, `approve` and
`queue_control`). The joiner process is `invitation.decode`,
`relationship.join` and `pqxdh.initiate` (`initiate`, `pqxdh.gleam:368`), followed by
the decryption of the `Accept` that makes the relationship `Active`
(`relationship.gleam`, `in_awaiting`). In detail:

- The hybrid identity: two signing keys and an agreement key, bound by a
  hybrid signature over the label and all three (`binding_message`,
  `identity.gleam:117`), verified by both halves on every decode
  (`read_public`, `identity.gleam:256`). An identity is a data
  constructor, so the attacker assembles its own, including ones that
  reuse an honest party's X25519 key under its own signing keys, which is
  the shape the identity-misbinding attack needs.
- The bundle: version, identity, the signed X25519 prekey and the signed
  ML-KEM prekey, each signature hybrid under its own label, verified by
  the joiner before use. The commitment is the hash of the whole bundle.
- The agreement: DH1, DH2, DH3 and the KEM shared secret into one HKDF
  under the handshake label (`derive_shared`, `pqxdh.gleam:605`), with
  nothing else in the input, as in the code.
- The session AD: the two identity fingerprints, joiner first
  (`associated_data`, `pqxdh.gleam:638`).
- The first ratchet message: a fresh ratchet key, the root step against
  the signed prekey, the chain step, the message key, and the AEAD over
  the Hello under the session AD and the header (`init_sender`,
  `ratchet.gleam:153`; `kdf_rk`, `ratchet.gleam:495`; `kdf_ck`,
  `ratchet.gleam:515`; `message_keys`, `ratchet.gleam:526`).
- The transcript signature: hybrid, over the label, the version, both
  identities in full, the bundle commitment, EK, CT and the whole ratchet
  message (`transcript`, `pqxdh.gleam:465`), made after the message is
  encrypted and verified by the inviter before any agreement
  (`check_transcript`, `pqxdh.gleam:557`).
- The inviter's side: the commitment check, both halves of the transcript
  signature, the agreement with the prekey secrets and the identity
  secret, decryption with the signed prekey as its first ratchet key pair
  (`init_receiver`, `ratchet.gleam:188`), and the DH step on receipt
  (`dh_ratchet`, `ratchet.gleam:344`) that gives it the chain the Accept
  is encrypted from.
- ML-KEM's implicit rejection: a ciphertext not produced by encapsulation
  to the key decapsulates to a value that depends on the secret key and
  the ciphertext, never to an error, so a mangled CT is a failed AEAD on
  the first message, as `pqxdh.gleam`'s module doc says.

### What is abstracted, and what each abstraction could hide

- **X25519 is oriented, not commutative.** The agreement of a joiner-side
  key J and an inviter-side key R is the term `dhpk(J, R)`, computable
  from either secret (`dhl` by the holder of J's secret, `dhr` by the
  holder of R's) and by nobody else. The textbook encoding, one function
  with the equation `dh(a, pk(b)) = dh(b, pk(a))`, is kept in the file
  behind `DH_EQUATION` but is not run: the inviter computes four
  agreements against attacker-chosen keys in one clause, and under the
  equation ProVerif does not finish any query that needs that clause in
  an hour on this machine. What the orientation gives up is the identity
  of `dhpk(X, Y)` with `dhpk(Y, X)`: an attack that needs an honest party
  to agree against a key in the opposite orientation from the one it was
  generated for cannot be represented. In this profile every X25519 key
  has one role for the life of a relationship (the joiner's identity, EK
  and ratchet keys are always the left operand; the SPK, the inviter's
  identity and the inviter's ratchet keys always the right one), and the
  honest processes only ever put their own secret on their own side, so
  no honest computation flips orientation. The attacker loses nothing it
  could do in reality against those computations. This is the one
  abstraction a reader has to accept.
- **The attacker respects types** (`set ignoreTypes = false`): it does not
  pass a tuple where a public key is expected. Every wire field in the
  profile has a fixed size and a total decoder (`keys.gleam` sizes every
  key; `wire.take` every field), so a type confusion between fields is
  not reachable in the implementation.
- **Hashes, HMAC, HKDF and the AEAD are ideal.** The two halves of a
  `KDF_RK` output are two independent one-way functions of its inputs;
  the AEAD key and nonce derived from a message key are one symbol. A
  weakness in SHA-256 or in the HKDF structure is out of scope; the
  vectors below are the check on those implementations.
- **ML-DSA-65 signatures are hedged** (they take fresh randomness), as in
  OpenSSL; Ed25519 signatures are deterministic. Neither scheme is
  malleable in the model; the Wycheproof malleability cases are the check
  on that for Ed25519.
- **Two messages.** The model stops when the joiner has authenticated the
  Accept. Later ratchet steps, skipped keys, the counters and the
  post-compromise behaviour of the ratchet are not modelled.
- **No retry, digest or phase machinery.** `offer.redeem`'s recognition
  of a retried Initial message, the single-use of a bundle and the
  outbox are not modelled; the inviter process answers one Initial
  message per bundle, which is what `offer.consume` enforces by moving to
  `Consumed` (`offer.gleam:82`).
- **The mailbox is the attacker.** Queues, capabilities, padding and
  envelopes are not modelled; `docs/formal/p.md` covers delivery.

## Queries

All nine queries are in `pairing.pv.in` in this order. `j` and `r` are the
joiner's and inviter's public identities, `t` the pair of the signed
transcript and CT (the pair matters only when a mutation drops CT from the
transcript), `sk`
the handshake secret SK and `mk` the first message key.

| | Property | Query |
| --- | --- | --- |
| Q1 | SK secret, joiner's view | `event(JoinerStarts(j,r,t,sk,mk)) && attacker(sk)` is unreachable |
| Q2 | first message key secret | `event(JoinerStarts(j,r,t,sk,mk)) && attacker(mk)` is unreachable |
| Q3 | Hello plaintext secret | `event(HelloSent(x)) && attacker(x)` is unreachable |
| Q4 | SK secret, inviter's view, for an honest joiner | `event(InviterAccepts(r,j,t,sk,mk)) && event(HonestJoiner(j)) && attacker(sk)` is unreachable |
| Q5 | inviter authenticates any joiner (injective, on both identities, the transcript and both keys) | `inj-event(InviterAccepts(r,j,t,sk,mk)) ==> inj-event(JoinerStarts(j,r,t,sk,mk))` |
| Q6 | inviter authenticates an honest joiner | `inj-event(InviterAccepts(r,j,t,sk,mk)) && event(HonestJoiner(j)) ==> inj-event(JoinerStarts(j,r,t,sk,mk))` |
| Q7 | joiner authenticates the inviter (injective, on both identities and SK) | `inj-event(JoinerActive(j,r,sk)) ==> inj-event(InviterSendsAccept(r,j,sk))` |
| Q8 | no unknown key share | `event(InviterAccepts(r,j,t,sk,mk)) && event(JoinerStarts(j2,r2,t2,sk,mk2)) ==> j = j2 && r = r2` |
| Q9 | the key binds the transcript (KEM re-encapsulation) | `event(InviterAccepts(r,j,t,sk,mk)) && event(JoinerStarts(j2,r2,t2,sk,mk2)) ==> t = t2` |

Q5 and Q6 differ only in whether the accepted identity has to be an
honest joiner's. Q5 is the statement "only the intended party can redeem
the invitation", which the profile does not claim (an invitation is a
bearer credential, spec section 4.2); Q6 is the statement it does claim,
that no one can make the inviter accept a session attributed to an honest
joiner's identity that the joiner did not start.

What the rows say, in protocol terms:

- **Secrecy and authentication hold in every hybrid scenario.** With
  X25519 and Ed25519 both broken, SK stays secret through the KEM shared
  secret, the joiner is authenticated by the ML-DSA-65 half of its
  transcript signature, and the inviter by the ML-KEM prekey secret only
  it holds. With ML-KEM and ML-DSA-65 both broken, SK stays secret through
  DH2 and DH3 (the joiner's ephemeral against the inviter's identity and
  signed prekey), the joiner is authenticated by DH1 and the Ed25519 half,
  and the inviter by the SPK secret.
- **A leaked invitation lets its holder redeem it, and nothing else.**
  Q5 fails because the attacker, holding the bundle, runs `initiate` with
  an identity of its own and the inviter accepts: the trace ProVerif
  reconstructs is exactly that, with no break of any primitive. Every
  other property survives the leak, in every scenario: the attacker learns
  nothing of an honest joiner's session with the same bundle (Q1 to Q4),
  cannot be accepted under an honest joiner's identity (Q6), cannot
  impersonate the inviter to an honest joiner (Q7, which needs the SPK and
  PQSPK secrets, which the file does not carry), and cannot cause an
  unknown key share (Q8, Q9). This is spec section 4.4's statement made
  precise: the invitation is a bearer credential, and the only thing the
  bearer gets is the inviter's acceptance of a session under the bearer's
  own fresh identity.
- **Forward secrecy against identity compromise holds; against prekey
  compromise it does not, by construction.** With both identities' secrets
  published after the session, SK still needs DH3 (the ephemeral against
  the signed prekey) and the KEM secret, neither of which an identity key
  gives. With the SPK and PQSPK secrets published too, every input of SK
  is recoverable from the recorded Initial message: DH1 from the joiner's
  identity secret, DH2 from the inviter's, DH3 and SS from the prekey
  secrets. The one thing that survives is the Hello plaintext (Q3 stays
  true): decrypting it needs the session AD, and the AD carries the
  inviter's fingerprint, which never crosses the network; with the
  invitation leaked as well (`fs_prekeys_leak`) it falls too. PQXDH without
  one-time prekeys has no better answer; what makes
  Pondline's SK forward secret is that the bundle is single-use and
  `offer.consume` drops the `Stock` holding both prekey secrets when it
  moves to `Consumed` (`offer.gleam:82`), and that `respond`'s decryption
  of the first message takes the DH ratchet step that replaces the SPK
  secret in the stored ratchet state (`dh_ratchet`, `ratchet.gleam:344`). The row is in
  the table so that a change to either is caught as a change in what is
  provable.
- **Identity secrets revealed before the session do not break the
  session's secrecy** (`lt_before`): SK is protected by the single-use
  prekeys and the joiner's ephemeral. With the invitation also leaked
  (`lt_before_leak`), Q4, Q5 and Q6 fail, and this is inherent: a compromised
  joiner holding the bundle can pair as itself. The attacker holds the
  joiner's signing and X25519 secrets, so it runs `initiate` as that joiner
  with an ephemeral of its own; the inviter accepts a session attributed to
  the joiner under a key the attacker knows. No check can tell that session
  from the real joiner's, because the attacker holds everything the real
  joiner would use. The honest joiner's own session stays secret (Q1 to Q3).

## Gate status

`check.sh -j 2 -k` exits 0: all 30 rows match. Two rows were corrected to
reach that, and an earlier run of the same table exited 1 on both.

- **`lt_before_leak`** expected `TTTTFFTTT` and got `TTTFFFTTT`. The model was
  right and the expectation had missed Q4, so the expectation changed to
  `TTTFFFTTT`. The bullet above says why the result is inherent.
- **`no_ct_weak_kem`** expected `TTTTFFTTF` and got `TTTTTTTTT`, because
  `NO_CT_IN_SIG` removes CT from the transcript and the events carried only
  the transcript, so no query could observe a re-encapsulated CT. The third
  argument of `JoinerStarts` and `InviterAccepts` is now the pair of the
  transcript and CT, and the row produces the attack it expected with no change
  to its expectation. Every other row gave the same letters before and after
  this change.

```text
                  RESULT event(InviterAccepts(r,j,t,sk,mk)) && event(JoinerStarts(j2,r2_1,t2,sk,mk2_2)) ==> j = j2 && r = r2_1 is false.
```

A variant that drops the KEM ciphertext from the KDF input, the mutation
the PQXDH analysis would suggest, has no faithful form here: the code's
KDF never took CT (`derive_shared`, `pqxdh.gleam:605`). What binds CT in
Pondline is the transcript signature, so the variant that answers the
question is `no_ct_weak_kem`, and `no_ct_weak_kem_kdf` shows the KDF would
bind it just as well.

Row times in seconds: `no_sig_leak_dh` 149, `no_sig_leak` 34, `no_ct_weak_kem` 27, `no_ct_weak_kem_kdf` 45, `ed_only_leak_quantum` 148, `ed_only_leak_ed` 34, `ml_only_leak_ml_dh` 249, `ml_only_leak_pq` 43, `no_ad_leak` 20, `no_ad` 18.
Each of the six ticket rows below takes under one second.

## The sealed invitation (tickets, ADR-009)

`formal/crypto/ticket.pv.in` models `core/ticket` (`keys`,
`ticket.gleam:264`; `seal`, `ticket.gleam:308`; `open`, `ticket.gleam:337`): the
ticket secret K reaches the joiner out of band; every key is a labelled
derivation from K; the blob is the version, `HMAC(commit_key,
invitation)` and the AEAD of the invitation under the key with the label
and the locator as associated data; the inviter hands the locator, the
retrieve capability and the blob to the mailbox, which is the attacker;
the joiner asks for the locator and opens whatever comes back, AEAD first,
then the commitment. The queries are T1, the invitation is secret from the
mailbox; T2, a joiner opens under its ticket only what the inviter sealed
for that ticket; and T3, one blob opens to one invitation under every
ticket, which is the key-committing property the commitment exists for.

A symbolic AEAD is committing by construction, so the property cannot be
tested without giving the attacker what ChaCha20-Poly1305 gives a holder
of two keys: `NONCOMMITTING_AEAD` adds a `dual` ciphertext that opens to
one plaintext under one key and associated data and to another under a
second pair.

| Row | Macros | T1 | T2 | T3 |
| --- | --- | --- | --- | --- |
| `ticket_base` | | T | T | T |
| `ticket_noncommitting` | `NONCOMMITTING_AEAD` | T | T | T |
| `ticket_no_commitment` | `NO_COMMITMENT` | T | T | T |
| `ticket_leak` | `LEAK_TICKET` | F | F | T |
| `ticket_leak_noncommitting` | `LEAK_TICKET NONCOMMITTING_AEAD` | F | F | T |
| `ticket_leak_nc_no_commit` | `LEAK_TICKET NONCOMMITTING_AEAD NO_COMMITMENT` | F | F | F |

```text
ticket_base:            RESULT not (event(Sealed(k,inv)) && attacker_bitstring(inv)) is true.
                        RESULT event(Opened(k,inv,b)) ==> event(Sealed(k,inv)) is true.
                        RESULT event(Opened(k,inv,b)) && event(Opened(k2,inv2,b)) ==> inv = inv2 is true.
ticket_leak_nc_no_commit: RESULT event(Opened(k,inv,b)) && event(Opened(k2,inv2,b)) ==> inv = inv2 is false.
```

This model matches the code on `main`: `core/ticket` and ADR-009 have not
changed since this branch's base. The labels, the extract salt, the blob
layout, the associated data (`associated_data`, `ticket.gleam:482`), the
AEAD-then-commitment order and the clear locator and retrieve capability
all agree. The model leaves out three things: the nonce (one symbol with the
key), the constant-time comparison, and the daemon's checks after `open`
(the invitation's decode and the route against the ticket's mailbox).

Read together: a mailbox without K learns nothing and substitutes nothing,
with or without the commitment, because the AEAD key is derived from K and
the locator is in the associated data. A holder of K seals what it likes,
which is the bearer property the ADR states. The commitment is load-bearing
in exactly one case, the one it was written for: when the AEAD is not
key-committing and two tickets have leaked (or were issued by the same
party), one stored blob can be opened to two different invitations under
the two tickets unless the commitment is checked. ProVerif finds that
attack when and only when the commitment check is removed.

What the ACVP suites cannot reach through this binding: ML-KEM key
generation from `(d, z)` and encapsulation from `m` (OTP exposes neither

the first of which is the reason the non-empty-context sigGen cases are
negative vectors here.

verification accepts all 29 Wycheproof small-order and mixed-order public

top bit set, or the value at or above the field prime) and reduces them as
RFC 7748 says, so two encodings of one public key give one shared secret
(finding 7).

## Where the code and the profile document differ

Read against `docs/crypto-profile-v1.md`, `docs/adr/005-hybrid-authentication.md`
and `docs/spec.md` sections 4 and 5. The model follows the code.

1. **`join_secret` (spec sections 4.2 and 4.3) is not implemented.** The
   invitation has no join secret and the Hello carries none
   (`invitation.gleam:5`); `docs/research/initiator-deniability.md` notes
   this. No query depends on it: the bundle's ML-KEM prekey already makes
   possession of the invitation necessary to redeem it (`base` Q5 is true
   with the invitation out of band, false with it leaked), and a join
   secret in the same file would leak with it. The spec text is the stale
   side.
2. **Spec section 4.3 step 2 has the joiner fetch the bundle and check it
   against commitments in the invitation.** The code embeds the bundle in
   the invitation (design review ruling, `invitation.gleam` module doc) and
   with tickets the invitation itself is fetched sealed (ADR-009). The
   model follows the code: there is no bundle fetch.
3. **ADR-005's body writes the transcript as `label || version || AD ||
   ...` with AD the two identity encodings; its addendum and the profile
   write the identities in full and make the session AD the two
   fingerprints.** The code is the addendum (`transcript`, `pqxdh.gleam:465`;
   `associated_data`, `pqxdh.gleam:638`). The bytes signed are the same under both readings.
4. **The profile says the KDF input is `0xFF x 32 || DH1 || DH2 || DH3 ||
   SS` and the code agrees** (`derive_shared`, `pqxdh.gleam:605`). Neither puts CT or
   PQSPK into the derivation; see finding 1.
5. **The profile's section 8 lists forward secrecy under the Double
   Ratchet** and does not say that the forward secrecy of SK itself rests
   on retiring the prekey secrets. The code retires them (finding 3); the
   profile should say so.

Everything else checked matches: the order of the responder's checks
(section 4), both halves on every verification, the labels (section 9),
`KDF_CK`'s 0x01 and 0x02 (`kdf_ck`, `ratchet.gleam:515`), the signed prekey as the
responder's first ratchet key pair (`init_receiver`, `ratchet.gleam:188`), implicit
rejection, hedged ML-DSA-65 with an empty context, and the sizes.

## Findings, by severity

None is a vulnerability in the implemented protocol under the profile's
stated assumptions. They are ordered by how much a reader of the profile
would want to know them.

1. **The handshake KDF does not bind the KEM ciphertext or public key;
   the transcript signature does** (low, design). Signal's PQXDH
   revision 3 section 4.12 binds `PQPKB` into AD for a generic KEM and
   relies on Kyber incorporating the public key for ML-KEM; the USENIX
   2024 analysis is where that requirement came from. Pondline binds CT
   through the hybrid transcript signature and PQSPK through the signed
   bundle commitment inside it, which the model shows is sufficient in
   every hybrid scenario (`weak_kem` all true, `leak_weak_kem` false only
   at Q5) and necessary (`no_ct_weak_kem` fails Q5, Q6 and Q9). The residual is that this
   binding is only as strong as the signature pair, whereas a KDF binding
   would hold even against a forger. ML-KEM is ciphertext- and
   public-key-binding for honestly generated keys (Cremers, Dax,
   Medinger, CCS 2024: LEAK-BIND-K-CT and LEAK-BIND-K-PK), and the only
   party able to produce the malformed decapsulation keys of Schmieg's
   MAL-BIND counterexamples is the inviter, who already holds every secret
   of the session; so the practical gap is nil. Recommendation for V2:
   add `CT || PQSPK` (or the bundle commitment) to the HKDF `info`, as
   `no_ct_weak_kem_kdf` models; it costs nothing on the wire.
   Evidence: rows `weak_kem`, `leak_weak_kem` and `no_ct_weak_kem`; `derive_shared`,
   `pqxdh.gleam:605`.
2. **The Ed25519 half of the transcript signature is redundant with DH1
   in the symbolic model** (informational). A verifier that checked only
   the ML-DSA-65 half has no attack unless X25519 is broken as well as
   ML-DSA-65 (`ml_only_leak_pq` fails only Q5, as the plain leak does;
   `ml_only_leak_ml_dh` also fails Q4 and Q6), because with ML-DSA-65 broken the
   joiner is still authenticated by DH1, exactly as in classical PQXDH.
   The ML-DSA-65 half is the one that does new work: it is what
   authenticates the joiner when X25519 and Ed25519 are both broken
   (`ed_only_leak_quantum` attacked, `quantum` proved). ADR-005's
   rationale that "a flaw in ML-DSA should not cost authentication
   outright" is served by DH1, not by the Ed25519 half. This changes no
   decision (the pair is cheap and uniform across the three signatures,
   and for the identity binding and prekey signatures the Ed25519 half is
   not redundant), but the ADR's reasoning for the transcript signature
   could say so.
   Evidence: rows `ml_only_leak_pq`, `ml_only_leak_ml_dh`,
   `ed_only_leak_quantum` and `quantum`.
3. **Forward secrecy of SK rests on prekey retirement, which the profile
   does not state** (low, documentation). `fs_prekeys` is the attack; the
   defence is `offer.consume` dropping `Stock` (`offer.gleam:82`) and the
   DH step inside `respond` (`dh_ratchet`, `ratchet.gleam:344`). Section 8 of the
   profile should name both, since either moving would turn a recorded
   handshake plus a later disk image into the session key.
   Evidence: rows `fs_longterm` (all true) and `fs_prekeys` (Q1, Q2, Q4 false).
4. **The session AD matters only when the invitation is leaked**
   (informational). The identity-misbinding attack that AD prevents needs
   the inviter's public identity, which never crosses the network
   (`no_ad` is fully proved; `no_ad_leak` is attacked). Leaked invitations
   are in scope (spec section 4.4), so AD stays; the point is that
   Pondline's handshake hides the inviter's identity from the mailbox
   entirely, which Signal's does not, and the profile could claim it.
   Evidence: rows `no_ad` (all true) and `no_ad_leak` (Q7, Q8, Q9 false).
5. **The sealed invitation's commitment is load-bearing in one case
   only** (informational, confirms ADR-009). Against a mailbox without
   K it adds nothing to the AEAD under a K-derived key with the locator as
   associated data (`ticket_no_commitment` fully proved). It is what stops
   one blob from opening to two invitations under two tickets when the
   AEAD is not key-committing (`ticket_leak_nc_no_commit`), which is the
   case the ADR wrote it for.
   Evidence: rows `ticket_no_commitment` (TTT), `ticket_leak_noncommitting`
   (T3 true) and `ticket_leak_nc_no_commit` (T3 false).
6. **Ed25519 verification accepts small-order and mixed-order public
   keys** (informational, pinned). OpenSSL checks the RFC 8032 equation
   without a cofactor or an order check on the key, so all 29 Wycheproof
   `acceptable` cases verify. No honest identity has such a key, every
   identity is also bound to an ML-DSA-65 key, and no trust derives from
   an Ed25519 key alone, so nothing here is affected; a future feature
   that compared Ed25519 keys on their own (a directory, a pin) would
   have to revisit this.
   Evidence: 29 `acceptable` cases of `ed25519_test.json`, pinned through
   `ed25519_verify`, `primitives_ffi.erl:66`.
7. **X25519 accepts non-canonical public key encodings** (informational,
   pinned). RFC 7748 masks the top bit and reduces, and OpenSSL does; the
   fingerprint hashes the encoding, so two encodings of one key are two
   identities with one agreement key, which an attacker cannot use
   without the secret.
   Evidence: the `acceptable` `NonCanonicalPublic` cases of
   `x25519_test.json`, pinned through `x25519`, `primitives_ffi.erl:50`.
8. **The spec's `join_secret` is unimplemented** (documentation; see
   difference 1). Nothing to change in the code.
   Evidence: the module doc of `invitation.gleam:5`, and row `base`, where
   Q5 holds with no join secret in the model.

Where these went: finding 1's V2 binding and findings 6 and 7 are recorded in
`docs/crypto-profile-v1.md` §10, finding 3 in its §8, findings 2 and 6 in the
addendum to ADR-005, and finding 8 in ADR-013. Findings 4 and 5 need no change.

## Open gaps

- **Post-compromise security of the ratchet** is not modelled: the model
  stops at the Accept. The profile's own statement that PCS is classical
  only (every DH step is X25519) is not checked here.
- **No computational proof.** The symbolic model treats SHA-256, HKDF,
  HMAC and the AEAD as ideal and the KEM as perfectly binding unless told
  otherwise; the CryptoVerif half of the PQXDH analysis has no
  counterpart here. The HKDF `info` and salt choices, the `0xFF` prefix
  and the use of one HKDF for both identity-fingerprint AD and keys are
  not examined beyond the vectors.
- **The oriented DH encoding** (above) is the one place the model is
  weaker than the equational theory. Running the `DH_EQUATION` form of
  the queries that need the inviter clause would need either a much
  larger time budget or Tamarin's built-in DH theory.
- **Side channels** are out of scope: constant-time comparison is used
  where the code says (`pqxdh.gleam`, `check_commitment`; `ticket.gleam`,
  `open`), but nothing here measures it, and the BEAM gives no memory
  erasure (profile section 8).
- **The ticket text layer** (`core/codex32`, the checksum, the endpoint
  encoding) and the mailbox's `PutBlob`/`GetBlob` authorization are not
  modelled; only the sealing is.
- **ML-DSA-65 known answers** cannot be reproduced through OTP 29 (no
  seeded key generation, hedged signing only); the ACVP checks here are
  the strongest available, and a deterministic-signing path, if OTP adds
  one, should be pointed at the `sigGen` deterministic cases.
- **Wycheproof has no ML-KEM or ML-DSA files at this commit** with the
  categories NIST's have; if they appear, they belong beside the ACVP
  ones.

## Changing the model when the profile changes

- A new field in the transcript, the KDF input or the AD: change the
  macro (`TRANSCRIPT`, `DERIVE_SK`, `SESSION_AD`) and run the whole
  table; the mutation rows say which property the field carries.
- A new signature scheme or a change to the hybrid rule: `HVERIFY` and the
  `hybrid` constructor; the `ONE_HALF_*` rows must still attack.
- A one-time prekey, a post-quantum ratchet step or a change to retirement:
  the `fs_prekeys` row is the one whose expectation should change.
- A new scenario: add a macro to the header of the source and a row with
  its expectation; a row whose letters surprise you is a finding, not a
  typo in the table.
- A new primitive: a vector file through `trim.py`, a test module that
  runs it through `primitives`, and a line in this document's tables.
- Re-pinning the vectors to a newer upstream commit: run `trim.py`
  against fresh checkouts, re-read the counts the tests assert, and record
  the new commit and hashes here.
