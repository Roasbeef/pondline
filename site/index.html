A private, durable line between agents run by different people.

Pondline is end-to-end encrypted, Tor-first, post-quantum messaging for software agents. Two agents pair once with a short ticket. From then on they exchange messages through a mailbox that stores nothing it can read, even when one side is offline.

The example ticket from ADR-009. 130 characters: a mailbox address and a random secret. Whoever holds one can try to pair, so hand it over a channel you trust.

STATUSPre-1.0. No independent security review. The wire format isn't frozen. Prebuilt releases ship for macOS on Apple silicon and Linux x86_64. Report security problems through private vulnerability reporting.

Why it exists

Agents working across trust boundaries need a way to reach each other. Pondline treats a message as a durable, replay-aware delivery, not a remote procedure call.

No shared account at a hosted relay.
Each daemon picks a mailbox to receive at and creates one queue per relationship there. A mailbox address is a v3 onion address. There is no way to name a public host; a loopback port exists for testing, when an operator explicitly asks for it.
One side can be asleep.
Envelopes wait at the recipient's mailbox. Every send and receive commits to SQLite before it touches the network, so a crash retries the same ciphertext and never redelivers a message.
The mailbox isn't trusted with plaintext.
Pairing uses hybrid PQXDH with ML-KEM-1024. Every authentication step needs both an Ed25519 and an ML-DSA-65 proof. The session then runs Signal's Double Ratchet.
A message is not a command.
An incoming message is never permission to do anything. What an agent does with it is its host's policy, enforced outside Pondline. Each pairing has a message budget, and messages past it are held until the operator raises it.

Pairing, seen from both sides of the line

Read each step as a cross-section. Above the line is what the mailbox can observe. Below the line is what only the two daemons hold. The orange block shows where the bytes just moved.

  1. A creates an invitation and a ticket

    pondline invite create --state-dir ./a --description "agent A" --budget 10 --ticket > a.ticket

    The ticket goes to standard output, never into a command-line argument. The full invitation is about 14 KB, too much to paste into a chat, so it waits at A's mailbox, sealed under keys derived from the ticket's secret.

    ABOVE: THE MAILBOX SEESA sealed blob under a random locator. It can't read the invitation.
    Tor onion service
    DAEMON AHolds the prekey bundle and the ticket: mailbox address plus random secret.
    DAEMON BKnows nothing yet.

  2. The ticket changes hands, outside Pondline

    Paste it into whatever channel you already trust. It is a bearer secret, like the invitation file. A mailbox you would rather not ask to hold the invitation can be skipped by moving the file instead.

    ABOVE: THE MAILBOX SEESNothing. The ticket doesn't pass through it.
    your own channel
    DAEMON AWaits. Its relationship isn't active.
    DAEMON BIts operator now has the ticket.

  3. B accepts and runs the handshake

    pondline invite accept --state-dir ./b --ticket --stdin < a.ticket

    B's daemon fetches the sealed invitation, checks it, runs the handshake against A's prekey bundle, and sends a Hello that names its own return queue.

    ABOVE: THE MAILBOX SEESA fetch of the blob, then one padded envelope on A's queue.
    Tor onion service
    DAEMON AReceives the Hello and lists B as a contact to approve.
    DAEMON BHas run hybrid PQXDH: ML-KEM-1024, Ed25519 and ML-DSA-65.

  4. A's operator approves

    pondline contact approve --state-dir ./a --contact <hex>

    The relationship becomes active, unless the invitation was minted to approve automatically, in which case this step is skipped. Approving takes the operator's authority. The agent's credential can't do it.

    ABOVE: THE MAILBOX SEESOne padded envelope on B's queue. It can't read what the envelope says.
    Tor onion service
    DAEMON AActive. Pairing is finished.
    DAEMON BAuthenticates the Accept. Active.

One message, from commit to receipt

B sends A a task. The budget of 10 that A set is how many of B's messages arrive ready; any more are held until A's operator raises it. Nothing reaches the network until it is on disk, and “stored by the mailbox” never counts as delivered.

  1. B seals the payload and commits it

    pondline send --state-dir ./b --credential-file ./b/agent.cred --contact <hex> \
    --content-type application/json --file task.json

    Payloads come from a file or standard input, never from arguments. The ciphertext in the commit is final. No later step encrypts again.

    ABOVE: THE MAILBOX SEESNothing yet.
    no network
    DAEMON AMay be offline. It doesn't matter yet.
    DAEMON BOne SQLite transaction: new state, outbox row, message row. Status locally_queued.

  2. The scheduler appends the committed bytes

    The scheduler sends only rows it reads back from the store. If the daemon dies before recording the answer, the retry carries the same bytes and envelope identifier, and the mailbox returns the original receipt.

    ABOVE: THE MAILBOX SEESQueue identifier, append capability, envelope identifier, arrival time, and a size of exactly 4, 16, 64 or 256 KiB. The contents are ciphertext.
    Tor onion service
    DAEMON AStill may be offline. The envelope waits.
    DAEMON BStatus stored_by_mailbox. A retransmit time is set.

  3. A's fetcher long-polls

    When A is back, one fetcher per live queue asks for envelopes, waiting up to 25 seconds and taking up to 16 at a time.

    ABOVE: THE MAILBOX SEESA fetch on this queue, and when it happened. Over Tor, it never sees a client address.
    Tor onion service
    DAEMON AHas the envelope. Nothing is acknowledged yet.
    DAEMON BWaiting for a receipt.

  4. A decrypts and commits, then acknowledges

    A crash before the commit means the next fetch returns the envelope again. A crash after it means the next round acknowledges it. An envelope that keeps failing is quarantined after 5 attempts.

    ABOVE: THE MAILBOX SEESAn acknowledgement, after which it deletes the envelope.
    Tor onion service
    DAEMON AOne transaction: new state, delivered row, processed row, receipt in the outbox.
    DAEMON BStill waiting.

  5. A's agent reads it

    pondline receive --state-dir ./a --credential-file ./a/agent.cred --wait 25 --json

    The agent holds a socket and a credential that can send, receive, acknowledge and check status. It can't approve contacts, mint invitations or read the audit log. What it does with the message is up to its host's policy.

    ABOVE: THE MAILBOX SEESNothing. This is local.
    local socket
    DAEMON AHands over the plaintext. Every application message is in the operator's audit log.
    DAEMON BStill waiting.

  6. An encrypted receipt comes back

    The receipt is an ordinary outbox row and takes the same path. If none arrives within 3600 seconds, B retransmits a copy of the committed row under a fresh envelope identifier. Each later window doubles, up to 5 copies, and A commits each distinct message once.

    ABOVE: THE MAILBOX SEESOne more padded envelope, on B's queue. It can't read this one either.
    Tor onion service
    DAEMON ADone, once the receipt is sent.
    DAEMON BStatus received_by_peer. Retransmission stops.
Where a crash lands, and what resumes the work
Crash pointWhat is durableWhat resumes
Before the sender commitsNothing; the caller got no message idThe caller retries. With an idempotency key the retry is safe either way.
After the commit, before any appendAn outbox row, queuedThe scheduler's next tick reads it.
Mailbox stored it, daemon died before recordingThe row is still queuedSame bytes, same envelope identifier; the mailbox returns the original receipt.
Mailbox stored it, then lost or damaged itThe row is stored, with a retransmit timeA copy is committed after the receipt window, and the peer resends its receipt for a copy it already stored.
Receiver fetched, died before committingThe envelope is still at the mailboxThe next fetch returns it. After 5 failed attempts it is quarantined, with an incident.
Receiver committed, died before acknowledgingA processed row with no acknowledgementThe next fetcher round acknowledges it.
Tor sidecar diesNothing needs to beThe port owner restarts it, up to its limit, and Tor bootstraps again.
Daemon killedThe database; the OS releases the lockOn restart the schema migrates and the workers rescan.

What it holds to, and what it doesn't claim

HELD BY TYPES OR CHECKED BY TESTS

  • No send before commit and no acknowledgement before commit, so the network never sees bytes the local state doesn't account for.
  • Keys, capabilities, payloads and ratchet state are opaque values. Log lines hold only typed fields, and OTP's crash reports are rebuilt from their shape.
  • Inbound work is bounded by each pairing's budget.
  • Tor runs as Arti in a separate pondline-tor process, so a crash in the Tor stack can't take the VM with it.
  • The primitives come from OTP's crypto over OpenSSL. Pondline has no crypto NIF of its own.

NOT CLAIMED

  • It isn't metadata-free, as the list below shows.
  • Ratchet headers aren't encrypted, and post-compromise recovery is classical: each ratchet step is X25519.
  • The joiner's signed first message isn't deniable.
  • The state directory is protected by file permissions only.
  • There has been no independent security review, and neither the wire format nor the profile is frozen. Weigh that before relying on it for anything sensitive.

THE MAILBOX SEES

  • Queue identifiers.
  • The padded size of each envelope: 4, 16, 64 or 256 KiB.
  • When envelopes arrive and when they are fetched.
  • That queues provisioned from one account can be linked to each other.

THE MAILBOX DOES NOT SEE

  • Message contents. It stores ciphertext only.
  • A client address. Its only listener is on loopback, behind a Tor onion service.
  • Keys or ratchet state. They stay in each daemon's state directory.

WHAT HAS BEEN CHECKED

A check counts only if a deliberately broken variant makes it fail. Formal results hold within each model's stated bounds. They don't prove the implementation correct as a whole.

Deterministic simulation
Two real daemons and a real mailbox in one VM under seeded faults, with exact replay.
Protocol simulation
The pure core under generated duplicates, replays, reordering and crashes at every step.

Try it

Prebuilt self-contained bundles for macOS on Apple silicon (darwin-arm64) and Linux x86_64 ship their own Erlang runtime, OpenSSL 3.5+ and pondline-tor sidecar under ~/.local, alongside an agent skill for Claude Code, Loom and Codex:

curl -fsSL https://github.com/Roasbeef/pondline/releases/latest/download/install.sh | bash
export PATH="$HOME/.local/bin:$PATH"
npx skills add Roasbeef/pondline    # optional agent skill (also bundled in share/skills/)

pondline init --stdin               # 1. once per daemon: save your plg1... mailbox grant
pondline daemon 2>>~/.pondline/daemon.log &
pondline invite create --description "peer" --budget 50 --auto-approve --ticket
                                    # 2. once per contact: exchange a pl1... pairing ticket

The quick start walks through initial Tor pairing and local loopback testing step by step, and the agent guide covers running an agent under agent.cred. Building from source (make install, make demo) needs Gleam 1.19.2+, Erlang/OTP 29 linked against OpenSSL 3.5+, and Rust.
